# 0001: Layout of the jarvis.modules packages

- **Status:** Accepted (Option A, migration in progress)
- **Date:** 2026-10-12
- **Deciders:** Andrew Morris

## Context

JARVIS is a uv workspace with three top level pieces: `jarvis-core`, `jarvis-app`, and `jarvis-modules`. Modules are grouped by type on disk (vision, audio, hardware, motion, simulator). The goal was a clean import path under `jarvis.modules` without a large pile of nested folders and pyproject.toml files.

Early attempts had a pyproject.toml at every level (root, `jarvis-modules`, each category, each leaf). That produced confusing workspace errors, such as `jarvis-camera references a workspace in tool.uv.sources ... but is not a workspace member`, because the `members` globs did not match where the tomls actually lived.

Constraints that shaped the options:

- Python import names map to folders, so `jarvis.modules.camera` needs three nested folders after `src`.
- `jarvis` and `modules` must have no `__init__.py`, because core, app, and modules all contribute to the `jarvis` namespace (namespace packages).
- Every workspace member glob must land on a folder that directly contains a `pyproject.toml`.
- uv only reads files named `pyproject.toml`, so a file like `modules.toml` is ignored.

## Options considered

### Option 0: One package per leaf, full nesting (rejected)

```
packages/jarvis-modules/vision/jarvis-camera/
  pyproject.toml
  src/jarvis/modules/vision/camera/__init__.py
```

Import: `jarvis.modules.vision.camera`.

Rejected because the folder depth after `src` felt excessive, and every module needed its own toml plus workspace and sources entries.

### Option B: One package per leaf, shallow folder mapped to a long import path

```
packages/jarvis-modules/vision/jarvis-camera/
  pyproject.toml
  src/
    __init__.py
    camera.py
```

with, in the leaf toml:

```toml
[tool.setuptools]
packages = ["jarvis.modules.camera"]

[tool.setuptools.package-dir]
"jarvis.modules.camera" = "src"
```

Import: `from jarvis.modules.camera import ...` (flat, no category in the path).

Pros:

- Shallow folders. Code sits directly under `src`.
- Each module is independently installable, with its own dependencies.
- The category folders (`vision`, `audio`) exist on disk only.

Cons:

- The folder names no longer match the import path, so editors and type checkers may not follow the mapping.
- Every new module needs its own pyproject.toml, a workspace match, and a sources entry in the modules toml.
- More tomls to keep consistent (names must match dependency entries exactly).

This was implemented partially. The commit that precedes the migration contains camera and face tracking in this form, imported like:

```python
from jarvis.modules.face_tracking import FaceTrackingNode
```

### Option A: A single jarvis-modules package, categories in the import path (chosen)

```
packages/jarvis-modules/
  pyproject.toml
  src/jarvis/modules/
    vision/
      camera/
      face_tracking/
      hand_tracking/
    audio/
      tts/
      stt/
    hardware/
      micro_controllers/
    motion/
      kinematics/
    simulator/
      atom_sim/
```

Import: `from jarvis.modules.vision.camera import ...`.

Dependencies live in one toml. Category groups are optional extras:

```toml
[project.optional-dependencies]
vision = ["opencv-python"]
audio = []
hardware = []
motion = []
simulator = []
```

The root depends on `jarvis-modules[vision,audio,hardware,motion,simulator]`. The workspace has exactly three members: core, app, modules.

Pros:

- One toml for all modules. Adding a module means creating a folder (and adding a dependency to the right extra if needed). No workspace or sources edits.
- Folder layout matches the import path, so tooling works without special mapping.
- The three nesting folders (`jarvis/modules`) are paid once, not per module.
- Optional extras keep the benefit of the category split.

Cons:

- Modules cannot be installed individually, only by category extra.
- The category becomes part of every import path, which is longer than Option B.
- Dependencies for all modules are managed in one file.

## Decision

Adopt **Option A**. This is a solo project, so independent installs of single modules offer little value, while the cost of many tomls and workspace entries is felt on every new module. Matching folders to import paths also keeps tooling predictable.

Naming rules going forward:

- Folder names use underscores (`face_tracking`), since hyphens are not valid in Python module names.
- No `__init__.py` in `jarvis` or `jarvis/modules`.
- `__init__.py` is fine in category folders and module folders.

## Consequences

- All imports change from `jarvis.modules.<name>` to `jarvis.modules.<category>.<name>`.
- All leaf `pyproject.toml` files and the `jarvis-<name>` folders are deleted.
- Leaf names are removed from the root dependencies and `tool.uv.sources`.
- Verification after migration:

```
uv sync
uv run python -c "from jarvis.modules.vision.camera import camera"
```

## How to revert to Option B

1. Recover the pre-migration state from git (the commit containing camera and face tracking in Option B form, or the tag below).
2. Restore one `pyproject.toml` per leaf with the `package-dir` mapping shown above.
3. List every leaf in the root `members` (for example `packages/jarvis-modules/*/*`), in the modules dependency list, and in `tool.uv.sources`.
4. Change imports back to `jarvis.modules.<name>`.

Suggested tag for the last Option B commit: `layout-option-b`.

## Notes for the future

- If modules ever need to ship to different deployments, or other people need to install only some of them, revisit Option B. The per leaf packaging is the better fit for that.
- A hybrid is possible: keep Option A as the default and split one heavy module (for example a large simulator) into its own workspace package without changing the import path, since namespace packages allow multiple distributions to share `jarvis.modules`.
